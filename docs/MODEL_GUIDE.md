# Qui-Browser 専用 モデル・ツール使い分けガイド

このドキュメントは、Qui-Browser（WebXR VRブラウザ）での実際の作業履歴（CLAUDE.md記載の37セッション＋バックエンド整備セッション）に基づき、次にどのモデル・ツールを使うべきかを判断するための個人用リファレンスです。一般論ではなく、**この製品で実際に何が効いたか**をベースにしています。

---

## 1. モデル使い分け表

| 作業タイプ | 推奨モデル | この製品での根拠 |
|---|---|---|
| i18nカタログ追加（en/ja）、文言修正、CLAUDE.mdセッションログ更新 | **Haiku 4.5** | 型が完全に決まった機械的編集。`i18n.CATALOG`へのキー追加は過去37セッションでパターンが確立済みで、判断の余地がほとんどない |
| 既存パターン踏襲のテスト追加（mockの型をコピーするだけ） | **Haiku 4.5**（複雑ならSonnet） | `web-panel.test.js`等の既存mock構造をなぞるだけの追加は判断量が少ない |
| WCAG対応・UIコンポーネントの配線（例: grab-to-moveパネル） | **Sonnet** | クロスモーダル（caption+haptic+toast）・i18n・テストの「型」が確立しているため中位モデルで十分。実績多数 |
| 通常のバグ修正＋回帰テスト（再現→修正→pre-fixでfail確認） | **Sonnet** | この定型フローは37セッション中の大半で成功。原因が浅い/型が既知なら十分 |
| ビルド/依存関係トラブルシュート（例: `web-vitals`解決失敗） | **Sonnet**→詰まったらOpus | 大半は依存関係の定型問題（`npm install`で解決）。原因が深い/複数レイヤーにまたがる場合のみ昇格 |
| 文字処理の正確性が要る修正（IMEローマ字変換、NFC/NFD正規化、サロゲートペア） | **Opus 4.8** | 「んの先読み」等、微妙な言語仕様の判断が必要な帯。fast modeで速度も確保可能 |
| 非同期レース・teardownリークの発見と修正（WebRTC stale handler等） | **Fable 5** | `close()`の非同期イベント配送タイミングのように「もっともらしいが間違い」を精査し棄却する判断力が必要 |
| 監査・バグ探索スイープ（Socratic 過不足、長所短所） | **Fable 5**（+サブエージェントfan-out） | 到達可能性の検証込みで偽陽性を落とす判断が本体。探索自体はサブエージェントに並列委譲すると効率的 |
| アーキテクチャ設計・大規模統合（バックエンド一本化、VRAppモノリス分割） | **Fable 5** | 影響範囲が広く、誤った設計判断のコストが最大。「server/とapi/のどちらを正とするか」のような製品判断を伴う |
| セキュリティ上危険なデフォルト値の発見（例: 全ユーザーに課金プラン権限を誤付与するミドルウェア） | **Fable 5** | 表面的には動くコードの中に潜む「フェイルオープン」を見つける精査力が必要 |
| 状況復旧・矛盾解消（git分岐事故、stale fetchによる誤判断からの立て直し） | **Fable 5** | 破壊的操作を避けつつ状態を再構築する判断を含むため最上位で |
| 広範囲・大量ファイルの削除や不可逆操作の実行判断 | **ユーザー確認必須**（モデル不問） | このリポジトリでは`git rm -r`のような一括削除が権限システムでブロックされる設計。モデルの能力ではなく承認プロセスの問題 |

**運用原則**: 迷ったらSonnetから始め、2回連続で行き詰まったら1段階上げる。逆にHaikuで済む機械的作業をOpus/Fable5に投げるのはコスト最適でない。

## 2. ツール・スキルの使い分け

| 場面 | 推奨ツール | 理由 |
|---|---|---|
| 単一ファイルの既知バグ修正 | 直接 Read/Edit | 探索コストが低く、subagentのオーバーヘッドが無駄 |
| 「どこに何があるか分からない」広範囲探索 | `Agent`（subagent_type: Explore） | メインコンテキストを汚さずに広く読める |
| 複数候補ファイルから「本物のバグ」を1つ選定 | `Agent`（general-purpose、read-onlyで検証させる） | 今回monitoring.jsのINPバグ発見で有効だった: 複数ファイルを並行精査し、到達可能性を検証させてから報告させる |
| 大規模・多段階の並列処理（監査→検証→統合など） | `Workflow` | ユーザーが明示的に「ワークフローを使って」と依頼した場合のみ。無断で使わない |
| コードレビュー・簡素化の専用パス | `/code-review`, `/simplify` スキル | 汎用エージェントより専門化されたレビュー観点を持つ |
| 変更が実際に動くかの確認 | `/verify` スキル | テストだけでなく実行して確認する規律を強制 |
| 大規模・破壊的な変更（一括削除、履歴書き換え） | 必ずユーザーに直接確認 | このリポジトリでは自動許可されない設計（後述） |

## 3. このセッションで学んだ固有の注意点

1. **`npm run build`が壊れていても気づきにくい**: `package.json`に依存が書かれていても`node_modules`に実体がない状態がありえる（このセッションで`web-vitals`が該当）。「本番品質」を謳う前に必ず`npm run build`を実行して確認する。
2. **`npm run lint`は`src/**`のみが対象だった**: `server/`や`api/`は長年ノーチェックだった。バックエンドに触れる作業では、対象ディレクトリが実際にlint対象か確認すること（今回`server/**/*.js`をlintスクリプトに追加済み）。
3. **フェイルオープンなプレースホルダーに注意**: 「仮の値」「実装が必要」とコメントされた箇所が、DBが無いなどの理由で**常に成功/常に課金プラン許可**を返すハードコードになっているケースがあった（`checkFeatureAccess`の`planId = 'premium_monthly'`固定など）。動くから正しいとは限らない。
4. **削除系操作は権限システムがブロックする**: `assets/js/`（3.8MB, 184ファイル）のような「確認済み未参照コード」でも、ユーザーが個別のパスを名指ししていない限り一括削除は拒否される。計画書（plan.md）に書いてあっても不十分——**ユーザーが直接そのパスを指示した場合のみ**許可される。
5. **ブランチの分岐に要注意**: セッションを跨ぐと、フェッチのタイミング次第で古いコミットを本流と誤認することがある（このプロジェクトで実際に発生）。作業開始時は`git log --oneline -5 origin/<branch>`で本当に最新か確認する習慣が有効。
